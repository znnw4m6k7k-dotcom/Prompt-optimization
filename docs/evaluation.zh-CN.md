# 评测方法

## 1. 目标

评测不是证明“提示词一定更好”，而是回答三个可复现的问题：

1. 增强后的提示词是否保留了原始意图和事实？
2. 是否补齐了执行所需的结构？
3. 质量提升是否值得额外的延迟和成本？

## 2. 黄金集

`evals/cases.jsonl` 每行一个用例：

```json
{
  "id": "zh-data-01",
  "prompt": "把这份推广费用表分析一下，写份报告给领导汇报",
  "target": "data",
  "locale": "zh-CN",
  "mustInclude": ["## 任务目标", "## 输出要求", "## 完成标准"],
  "minScore": 80
}
```

覆盖维度：

- 七种 target；
- 中英文；
- 短草稿、长草稿；
- 信息完整与信息缺失；
- 含数字/专有名词；
- 含提示注入文本；
- 含不可执行或高风险请求；
- 输出长度上限。

## 3. 运行

```bash
npm run eval
```

使用远程 Provider：

```bash
PROMPT_REFINERY_PROVIDER=openai \
PROMPT_REFINERY_MODEL=your-model-id \
OPENAI_API_KEY=... \
npm run eval
```

输出：

- 每个用例是否通过；
- mustInclude 命中情况；
- rubric 分数；
- 延迟；
- 总通过率、平均分、p50 延迟。

`--json` 输出机器可读结果，便于 CI。

## 4. 指标

### 自动指标

| 指标 | 说明 | 门槛建议 |
| --- | --- | --- |
| 结构完整率 | mustInclude 全部命中 | ≥ 95% |
| JSON 可解析率 | Provider 返回可解析结构 | ≥ 99% |
| rubric 平均分 | 100 分制 | ≥ 80 |
| 长度合规率 | 不超过 maxChars + 10% | ≥ 95% |
| p50 延迟 | 本地/网络分别统计 | 按产品预算 |

### 人工指标

| 指标 | 评估方法 |
| --- | --- |
| 意图保持 | 双人盲评，比较原始需求与增强提示 |
| 事实新增 | 标注增强提示中原文没有的事实 |
| 可执行性 | 下游 Agent 是否减少追问 |
| 偏好胜率 | 原始 vs 增强，成对盲评 |

建议每季度重跑一次，并在更换模型、修改编译器提示、调整 rubric 时强制回归。

## 5. Rubric 的局限

当前 rubric 是结构启发式：

- 可能被“堆章节”刷高；
- 不能判断语义正确性；
- 不能发现所有事实编造；
- 对非模板化但高质量的提示可能偏保守。

因此：

- rubric 只作为回归门槛，不作为唯一质量结论；
- 关键发布必须配合人工抽检；
- 不把 LLM-as-judge 的分数当作真值，需与人工评分做相关性校准。

## 6. 后续评测路线

1. 增加“意图保持”标注集；
2. 增加事实一致性检查（数字、实体、日期）；
3. 用下游任务成功率作为最终指标；
4. 建立多模型对比面板；
5. 对 LLM judge 做偏差校准，只用于低成本预筛。
