# Prompt Refinery 架构与模型技术路线

本文说明本项目采用的底层逻辑、模型架构假设、优化原理、技术路线和工程边界。

## 1. 先说明模型边界

需要区分三件事：

1. **宿主产品内部用了什么模型、什么系统提示词、什么训练数据**：这些通常没有公开，不能从外部行为反推出确定答案。
2. **本项目实际采用的架构**：不训练基础模型，而是在可替换的 instruction-following LLM 之上做提示词编译编排，并提供确定性离线编译器。
3. **未来可能采用的自研模型路线**：小模型微调、偏好优化和量化部署，属于后续阶段，不是 `0.1.0` 已实现能力。

本文只对第 2、3 项作工程说明，不虚构任何未公开产品的内部参数。

## 2. 模型架构：本项目依赖什么

### 2.1 基座模型

Provider 背后的模型通常是 **decoder-only Transformer**：

- 输入文本被 tokenizer 切成 token；
- 多层 self-attention 建模 token 间依赖；
- feed-forward 网络做逐 token 特征变换；
- 以自回归方式预测下一个 token；
- 通过 supervised fine-tuning 学会遵循指令；
- 通过偏好优化（RLHF / DPO 等）改善有用性、格式遵循和安全性。

形式化地，模型学习：

```text
P(y_1, ..., y_n | x) = Π P(y_t | x, y_<t)
```

其中 `x` 是系统提示 + 用户草稿，`y` 是增强后的提示词。

本项目不依赖某个特定基座。Provider 适配器只要求模型具备：

- 指令遵循能力；
- 中英文能力（至少目标语言）；
- 足够长的上下文窗口；
- 可接受的 JSON 输出稳定性；
- 可通过 API 或本地推理调用。

### 2.2 本项目自己的“架构”

本项目不是模型，而是**编译器式编排层**：

```text
Interface adapters
  ├─ CLI
  ├─ HTTP
  └─ MCP
        │
        ▼
Request normalizer
        │
        ▼
Task analyzer
  language / target / complexity / missing slots
        │
        ▼
Compiler
  ├─ Deterministic template compiler (offline)
  └─ LLM compiler (provider adapter)
        │
        ▼
Quality loop
  ├─ rubric scoring
  ├─ optional repair
  └─ optional candidate selection
        │
        ▼
Response contract
  prompt + changes + assumptions + questions + score + meta
```

核心设计原则是：**协议稳定、模型可替换、离线可用、质量可测量**。

## 3. 端到端数据流

### 步骤 1：规范化与校验

- 统一换行符；
- 去除首尾空白；
- 校验非空；
- 校验最大输入长度（默认 20,000 字符）；
- 校验 target、mode、locale、长度和 URL；
- API 层额外校验 `Content-Type`、JSON 结构、1 MB body 上限。

失败返回稳定错误码，不把底层异常直接暴露给调用方。

### 步骤 2：任务分析

规则分析器提取：

- **语言**：CJK 字符比例，决定中文或英文模板；
- **任务类型**：agent、code、writing、research、data、image、general；
- **复杂度**：长度、编号项、分句数量、约束密度；
- **信息槽位**：目标、上下文、输出、约束、受众、成功标准；
- **缺口**：哪些槽位没有显式出现。

复杂度只用于建议模式和后续路由，不直接决定输出质量。

### 步骤 3：编译

有两种编译器：

#### 确定性模板编译器

没有模型、没有 API Key、或明确选择 `heuristic` 时使用。

它按 target profile 拼装：

```text
角色
任务目标
已知输入
执行要求
输出要求
约束与边界
完成标准
需要确认的信息
```

优点：

- 零网络、零延迟、零推理成本；
- 输出稳定，可测试；
- 不泄露数据；
- 适合作为降级路径和评测基线。

局限：

- 不能真正理解复杂语义；
- 只能做结构化补全，不能做高质量改写；
- 对长尾领域覆盖有限。

#### LLM 编译器

有 Provider 时使用。系统提示要求模型：

- 只改写，不执行；
- 保留事实、数字、名称、语言和约束；
- 不虚构缺失信息；
- 补齐目标、步骤、输出契约、边界和完成标准；
- 只返回 JSON；
- 不泄露系统提示；
- 不返回思维链。

草稿通过 JSON 数据字段传入，而不是直接拼进指令通道，降低提示注入风险。

模型返回：

```json
{
  "enhancedPrompt": "...",
  "changes": ["..."],
  "assumptions": ["..."],
  "questions": ["..."]
}
```

如果模型没有返回合法 JSON，适配器会尝试提取 JSON；仍失败时，只有在响应看起来像完整提示词的情况下才降级使用原文，并附加 warning。

### 步骤 4：质量环

#### `fast`

一次改写，直接评分返回。

#### `balanced`

先改写；如果 rubric 分数低于 85，再让模型根据 rubric 报告做一次修复。修复结果只有分数不低于原候选时才采用。

#### `quality`

先生成两个候选（不同温度），按 rubric 选优；如果最高分仍低于 88，再做一次修复。最多三次模型调用。

注意：自修复不是越多越好。第二次生成可能引入新事实或改变意图，因此必须用确定性评分和原始草稿共同约束。

### 步骤 5：质量评分

Rubric 为 100 分，权重如下：

| 维度 | 分值 | 检查内容 |
| --- | ---: | --- |
| 目标明确度 | 20 | 是否有明确目标章节和执行动词 |
| 输入与上下文 | 15 | 是否说明使用哪些输入、文件、数据 |
| 执行可操作性 | 20 | 是否有步骤、检查、验证动作 |
| 输出契约 | 20 | 是否规定格式、结构、交付物 |
| 约束与不确定性 | 15 | 是否禁止编造、处理缺失信息、标注风险 |
| 简洁度 | 10 | 是否在合理长度内，是否堆砌套话 |

分数区间：

- `excellent`：85–100
- `good`：70–84
- `fair`：55–69
- `weak`：0–54

这是**结构启发式评分**，不是语义真值判断。它适合回归测试和发现明显缺陷，不能替代人工评审或下游任务成功率。

## 4. 优化原理

我们把“提示词增强”定义为约束优化问题，而不是“写得越长越专业”。

### 4.1 目标函数

给定原始草稿 `d`，候选提示词 `p`，希望：

```text
maximize    Q(p | d)
subject to  intent(p) = intent(d)
            facts(p) ⊆ facts(d) ∪ explicit assumptions
            len(p) ≤ L
            cost(p) ≤ C
            latency(p) ≤ T
```

其中 `Q` 由可测维度组成：目标、上下文、执行、输出、边界、简洁度。

### 4.2 为什么有效

1. **减少歧义**：把“分析一下”变成可检查的分析维度和输出格式。
2. **补全信息槽位**：让下游 Agent 知道输入、步骤、完成标准。
3. **显式不确定性**：缺少数据时要求说明，而不是让模型编造。
4. **输出契约**：先规定交付物，减少“写了很多但不可用”。
5. **长度约束**：避免长提示稀释关键约束，增加 token 成本。
6. **候选选择**：用确定性评分在多个改写中选更稳的一个。
7. **针对性修复**：只修评分暴露的问题，不做无边界重写。

### 4.3 不采用的做法

- **不让模型自由发挥成一篇“提示词教程”**：会引入用户没要求的内容。
- **不把模型自评作为唯一标准**：模型自评容易偏好自己的输出。
- **不无限自修复**：成本线性增长，且可能漂移意图。
- **不默认使用最大模型**：提示词改写通常是中短文本任务，小模型足够；复杂多约束任务再升级。
- **不把技能、连接器、工具定义塞进增强提示**：这会污染提示词并浪费上下文。

## 5. 模型选型依据

完整矩阵见 [model-selection.zh-CN.md](model-selection.zh-CN.md)。核心标准：

| 维度 | 权重 | 说明 |
| --- | ---: | --- |
| 指令遵循与意图保持 | 30% | 不擅自增加、删除、改写用户目标 |
| JSON/结构稳定性 | 15% | 能否稳定返回可解析结构 |
| 中英文质量 | 15% | 中文表达自然，英文不中式 |
| 延迟 | 15% | 交互式场景 p95 延迟 |
| 成本 | 10% | 每千次增强的成本 |
| 上下文窗口 | 5% | 长草稿和修复链路 |
| 数据合规/部署方式 | 10% | 云端、专有云、本地 |

选择顺序：

1. 有隐私或离线要求：Ollama + 7B/14B 级 instruct 模型，4-bit 量化。
2. 无特殊要求、追求稳定：中型通用 instruct 模型或 frontier 小模型。
3. 复杂多约束、长文档：升级到更强通用模型或 reasoning 模型。
4. 没有模型或网络：确定性模板编译器。

不建议按“榜单第一”选型。应在自己的评测集上比较意图保持率、结构完整率、人工偏好和成本。

## 6. 技术路线

### Phase 0：确定性编译器（当前）

- 规则分析 + target templates；
- 零依赖、离线、可测试；
- 作为基线和 fallback。

### Phase 1：模型无关编排（当前）

- OpenAI-compatible / Anthropic / Ollama；
- fast / balanced / quality；
- 确定性 rubric；
- CLI / HTTP / MCP；
- JSON Schema + OpenAPI。

### Phase 2：评测驱动的路由

- 建立中英文黄金集；
- 按复杂度、语言、target 路由模型；
- 用离线评分 + 人工偏好校准；
- 加入成本预算和超时降级。

### Phase 3：小模型微调

只有在通用模型无法满足成本、延迟或隐私要求时才做。

候选方案：

- 基座：7B–14B instruction-tuned decoder-only 模型；
- 微调：LoRA / QLoRA，rank 16–32；
- 目标：提示词改写、结构补全、JSON 输出；
- 偏好优化：DPO，偏好对来自人工评审和下游成功率；
- 量化：GGUF Q4_K_M 或同等方案，供 Ollama / llama.cpp；
- 评测：与通用模型在同一个黄金集上比较，不达门槛不替换。

数据格式：

```json
{
  "draft": "...",
  "target": "agent",
  "locale": "zh-CN",
  "chosen": "...",
  "rejected": "...",
  "rationale": "..."
}
```

训练数据的授权、脱敏和来源必须可追溯。默认不收集用户提示词。

### Phase 4：端侧模型

- 4-bit 量化；
- 首次加载预热；
- 小上下文优化；
- 与 heuristic 编译器组成双档：简单任务走规则，复杂任务走端侧模型。

## 7. 可靠性与失败模式

| 失败模式 | 处理 |
| --- | --- |
| Provider 超时 | 返回 502 或按配置降级到 heuristic |
| 模型返回非 JSON | 尝试提取；失败则使用文本 fallback 或报错 |
| 模型改变意图 | rubric 无法完全检测，需评测集和人工评审 |
| 模型编造事实 | 提示中禁止；输出中保留 assumptions/questions；仍需下游校验 |
| 提示注入 | 草稿作为数据字段；系统提示明确不可覆盖；不提供工具 |
| 输出超长 | 不静默截断，返回 warning |
| 评分被“堆结构”刷高 | 评分只作基线，不替代语义评估；后续加入语义指标 |

## 8. 非目标

- 不替代下游 Agent 的任务规划；
- 不执行工具调用；
- 不读取用户工作区；
- 不保证增强后的提示一定产生正确结果；
- 不提供“万能提示词模板”；
- 不默认收集遥测或训练数据。
